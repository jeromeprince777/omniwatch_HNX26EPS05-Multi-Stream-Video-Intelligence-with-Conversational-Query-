# 02 — Research contribution, baseline, ablation, evaluation protocol
Worth 30% (accuracy) + 10% (latency) + 20% (research contribution) of the rubric. This file is the contract for how we measure.

## 1. Systems under test
| ID | System | Purpose |
|---|---|---|
| B1 | **Baseline (primary):** open-vocab detector (same one as ours) on sampled frames -> CLIP crop embeddings -> cosine to query text -> top-K detections, no tracking, no query parsing, no attributes | "Standard open-vocab detection + embedding retrieval" as the statement describes |
| B1+ | B1 given our parser/KB filters (camera + time) | Fairness check: isolates what tracklets/attributes/verification add beyond filtering |
| B2 | Whole-frame CLIP retrieval | Weak reference |
| B0 | (optional, if time) query-time OWLv2 or Grounding DINO on candidate frames | Strong but slow reference; shows latency/accuracy trade-off |
| OW-fast | Our system without VLM verification | Latency-competitive mode |
| OW-full | Our system with VLM verification | Accuracy mode |
Baseline must use the same footage, same sample FPS, same hardware, same text encoder size where possible. Document any difference. Do not weaken the baseline on purpose.

## 2. Our method (what is new vs baseline)
1. **Tracklet-level index.** Aggregate crop embeddings per track; one result per object passage instead of many near-duplicate frame hits; better recall for brief or blurred frames.
2. **Structured query decomposition.** Parser separates object, attributes, location, time; filters shrink the candidate set before similarity.
3. **Explicit attribute fusion.** Color naming and carries-association fix known weaknesses of embedding-only color and compound matching.
4. **Verification pass (P1).** VLM yes/no on top-K candidates trades latency for precision.
5. **Persistent referent KB.** Location phrases resolve to cameras/regions without asking again.
Each is an ablation row. If a component does not help on the dev set, say so in the write-up; negative results are acceptable, hidden ones are not.

## 4. Query set
- Dev set (tune thresholds, weights): >= 30 queries. Test set (touch once, at the end): >= 40 queries, from video segments not used for dev.
- Mix: color+object ("red car"), person+attribute ("person carrying a large bag"), location-constrained ("at the main gate"), time-constrained ("between 09:10 and 09:20"), existence yes/no, **negatives** (true answer is "no match", >= 20% of queries), hard cases (night, small objects, occlusion).
- Write queries the way a judge would, not the way our parser likes. Have a teammate who did not build the system write half of them.
- Schema `eval/queries/*.jsonl`: `{"id","text","type","gt":[{"camera_id","t_start","t_end"}],"expects_no_match":false,"needs_referents":["main gate"],"notes"}`.

## 4b. Referent handling during eval
Preload the KB with the referents the queries need (as if clarified once), and run a separate KB test for the clarification behavior (06). Do not let clarification prompts block automated eval.

## 5. Metrics
- **Hit@k (k=1,5):** a returned result is correct if camera == GT camera and its [t_start,t_end] overlaps the GT interval within tolerance tau (report tau = 5 s and 15 s). Hit@k = any of top-k correct.
- **MRR** over first correct result.
- **Existence accuracy:** yes/no correctness, including negatives; report false-positive rate on negatives.
- **Localization error:** distance in seconds between returned interval and GT interval (0 if overlapping), median and p90, on correct-camera hits.
- **Latency:** per query, end to end (parse + retrieve + verify + answer build) on a warm process; p50/p95; also cold-start time once. Same machine, no other load. Baseline timed the same way.
- Report n for every metric and a bootstrap 95% CI if time allows. With small n, say so.

## 6. Protocol rules
1. Freeze code + thresholds, then run test set once. Save raw per-query outputs, not just aggregates.
2. All thresholds picked on dev only. Record them in `eval/results/config_used.json`.
3. No manual tuning per query. No query-specific rules.
4. Same random seeds and sampling for every system.
5. Write-up tables are generated by script from `eval/results/*.json`.

## 7. Threats to validity (put a short version in the write-up)
Small query set; our own labeling; dataset bias toward our scenes; baseline strength is a choice (we also report B1+ and optionally B0); latency depends on hardware.
